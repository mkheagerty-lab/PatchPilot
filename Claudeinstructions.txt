================================================================================
1. WHAT PATCHPILOT IS
================================================================================

PatchPilot is a multi-tenant MSP patch management console that closes the gap
between Microsoft Defender Vulnerability Management (MDVM) — which only
surfaces vulnerabilities — and actual remediation. It is inspired by
Roboshadow's "Cyberheal" product, which uses Winget under the hood.

CORE VALUE PROPOSITION
----------------------
MDVM tells you what's vulnerable. Intune tells you what's deployed. Neither
gives you a single console where an MSP engineer can see a CVE, click a button,
and patch it across one device, a group, or on a schedule — using Winget for
third-party apps and Windows Update Agent for OS patches. PatchPilot is that
console.

TARGET USER
-----------
MSP engineers managing multiple customer tenants via GDAP (Granular Delegated
Admin Privileges).

2.3 SCRIPT GENERATION (REAL, REUSABLE OUTPUT)
---------------------------------------------
The prototype generates real, deployable scripts for:

WINGET REMEDIATION (THIRD-PARTY APPS)
--------------------------------------
# Runs as SYSTEM via Intune Remediation or Live Response
$ErrorActionPreference = 'Stop'
$wingetPath = (Get-ChildItem -Path "C:\Program Files\WindowsApps" `
  -Filter "Microsoft.DesktopAppInstaller_*" -Directory |
  Sort-Object Name -Descending | Select-Object -First 1).FullName
$winget = Join-Path $wingetPath 'winget.exe'
& $winget upgrade --id <PACKAGE_ID> --silent `
  --accept-source-agreements --accept-package-agreements --force
exit $LASTEXITCODE

DETECT SCRIPT FOR INTUNE REMEDIATION
-------------------------------------
$installed = & $winget list --id <PACKAGE_ID> --exact
if ($installed -match '<MIN_VERSION>') { exit 0 } else { exit 1 }

WINDOWS UPDATE AGENT REMEDIATION (OS PATCHES)
----------------------------------------------
# Option A — PSWindowsUpdate
Install-Module PSWindowsUpdate -Force -Scope AllUsers
Import-Module PSWindowsUpdate
Get-WindowsUpdate -KBArticleID <KB_ID> -Install -AcceptAll -IgnoreReboot

# Option B — Native WUA COM (preferred for Live Response — no module dep)
$session = New-Object -ComObject Microsoft.Update.Session
$searcher = $session.CreateUpdateSearcher()
$results = $searcher.Search("IsInstalled=0 and Type='Software'")
# ... download + install + report exit code

3. THE REMEDIATION EXECUTION MODEL
================================================================================

This is the core IP of PatchPilot. The real build must implement all four
execution channels:

CHANNEL                     LATENCY    USE CASE                  GRAPH ENDPOINT
--------------------------- ---------- ------------------------- --------------
Defender Live Response      seconds    Critical zero-day,        POST /api/machines/{id}/runliveresponse
                                       single device, ad-hoc     (Defender API host)
On-demand Intune            1–5 min    Most third-party          POST /deviceManagement/managedDevices/{id}/initiateOnDemandProactiveRemediation
Remediation                            patches, per-device/group
Win32 app + device sync     5–15 min   Group-level deployments   POST /deviceManagement/managedDevices/{id}/syncDevice
Expedited Quality Update    hours      OS patches, push specific POST /deviceManagement/windowsQualityUpdateProfiles
                                       KB to group fast

TIERED OS PATCH MODEL
---------------------
URGENCY                       CHANNEL
Critical zero-day, patch now  Live Response > WUA script (immediate) +
                              Update Ring as backstop
Important, this week          Expedited Quality Updates
Standard cadence              Update Ring with normal deferrals

IMPORTANT CAVEATS BAKED INTO THE DESIGN
----------------------------------------
  - Live Response requires Defender for Business Premium or MDE P2 — gracefully
    degrade if not licensed
  - OS patches via Live Response kick off the install but reboot handling must
    go through Intune Update Ring policy
  - WSUS / deferral policies may block scripted WUA calls
  - Per-tenant licensing must be detected and UI gracefully disabled when
    features aren't available

5. AUTHENTICATION & GDAP MODEL
================================================================================

This is the part the prototype could not implement and is the biggest piece of
work.

AUTH FLOW
---------
  1. MSP engineer signs into PatchPilot using Entra ID
     (OIDC / Authorization Code + PKCE) against the MSP tenant
  2. App acquires a token for the MSP tenant (standard delegated flow)
  3. For actions in a customer tenant, app does OBO (On-Behalf-Of) token
     exchange against /{customerTenantId}/oauth2/v2.0/token to get a delegated
     token scoped to that customer tenant
  4. Azure AD validates:
       - GDAP relationship grants the engineer the right roles in the customer
         tenant
       - The PatchPilot app has been admin-consented in the customer tenant
  5. Token is cached server-side (encrypted), refreshed as needed

PER-TENANT CONSENT
------------------
GDAP ALONE IS NOT SUFFICIENT. Every customer tenant must separately consent to
the PatchPilot app. The prototype includes a consent URL generator + email
templates for this onboarding flow — they should be carried forward.

Consent URL pattern:
  https://login.microsoftonline.com/{customerTenantId}/adminconsent
    ?client_id={patchpilotAppId}
    &redirect_uri={yourRedirectUri}

LICENSING DETECTION PER TENANT
------------------------------
Before exposing actions, probe each tenant's SKUs to detect:
  - Intune (Remediations, Expedited Updates)
  - Defender for Business / Defender for Business Premium (Live Response)
  - MDE P2

UI should gracefully disable unsupported channels per tenant with a tooltip
explaining why.

6. ARCHITECTURE FOR THE REAL BUILD (SELF-HOSTED, NO CLOUD PAAS)
================================================================================

STACK RECOMMENDATION
--------------------
LAYER             TECHNOLOGY
Frontend          React + TypeScript + Vite + Tailwind + shadcn/ui
                  (carry over the prototype UI 1:1)
Backend           Node.js + Fastify (or NestJS) — single binary, easy to
                  self-host
Auth library      @azure/msal-node (Microsoft official, no Azure subscription
                  needed)
Database          PostgreSQL (self-hosted) or SQLite (single-instance)
Job queue         BullMQ + Redis (self-hosted) for scheduled / queued
                  remediation jobs
Reverse proxy     Caddy or nginx
Container         Docker + docker-compose for single-host deployment
Secrets           .env file with file-permission lock-down, or HashiCorp Vault
                  if scaling
Audit log         Postgres table + optional Loki / Grafana for visualisation

WHY THIS STACK
--------------
  - 100% self-hostable on any Linux box, VPS, or on-prem server
  - Zero cloud PaaS dependencies (no Azure, AWS, GCP, SharePoint,
    Power Platform)
  - All token handling server-side (browser never sees a Graph token)
  - MSAL Node handles OBO, refresh tokens, GDAP token exchange correctly
  - BullMQ handles the scheduling / job state for recurring remediations
  - Standard Postgres = easy backup, easy migration, no vendor lock-in

DEPLOYMENT MODEL
----------------
Single docker-compose.yml running:
  - patchpilot-web    (frontend, static files served via Caddy)
  - patchpilot-api    (Fastify backend)
  - patchpilot-worker (BullMQ worker for scheduled jobs)
  - postgres
  - redis
  - caddy             (TLS termination + reverse proxy)

MSP runs this on:
  - An on-prem server, or
  - A small VPS (Hetzner / Linode / DigitalOcean / their existing infra), or
  - A NUC in their office

REVERSE PROXY + HTTPS
---------------------
Caddy auto-provisions Let's Encrypt certs. The redirect URI for the Entra app
registration becomes:
  https://patchpilot.<msp-domain>.com/auth/callback

10. NON-NEGOTIABLES / DESIGN PRINCIPLES
================================================================================

  1. No Azure, no SharePoint, no Power Platform, no Dataverse.
     Fully self-hosted.
  2. All tokens server-side. Browser never sees a Graph access token.
  3. Audit everything. Every Graph call logged with: engineer, tenant,
     endpoint, payload hash, response status, timestamp.
  4. Graceful licensing degradation. Never expose a button for a feature the
     tenant isn't licensed for.
  5. Per-tenant safety. A single misconfiguration must never cascade across
     tenants. Token cache, job queue, audit log all keyed by tenant.
  6. Read-only first. Every new tenant integration starts read-only; write
     actions opt-in per tenant.
  7. Deploy script is sacred. The Deploy-PatchPilot.ps1 is real and works —
     keep it as the canonical onboarding artefact.
